# Multi-user hosting — the plan

**Node host only.** Nothing here changes the VS Code extension. Where core has to grow, it grows
an *optional* seam that `apps/host` supplies and `apps/vscode` leaves undefined, so the extension
behaves exactly as it does today. That is §4's rule applied to a feature rather than a platform.

Decided 2026-08-22 with the user. Three choices were made up front because each one changes what
gets built rather than only how:

| Question | Decision |
|---|---|
| How users prove who they are | A **trusted reverse-proxy header**. IIS or nginx terminates Kerberos/NTLM/OIDC; Light Code reads the user from a header and trusts it only from a configured upstream. |
| What the **programming provider** does | **Writes the code, as a sub-call.** When a Python tool is created or updated, the source is generated by that provider in a separate request and returns into the normal approval flow. |
| What happens when a normal user creates a tool or skill | **Queued for an admin.** The turn is told it was submitted and continues; nothing is registered or runnable until an admin approves it. |

---

## What this does not buy, stated first

**Per-user scoping here is organisational, not enforced.** Every user's agent still runs shell
commands, MCP servers and Python tools as the *service account*. So one user's agent can read
another user's secrets file, or simply run `env`. Per-user API keys and per-user variables are
separated in storage and in the UI, and they are **not secret from another user of the same
server**.

This is §14's unchanged gap: the real fix is one OS account or container per session, with the
server as a supervisor, and it is not built. `docs/hosting.md` says so and must keep saying so.
The admin UI has to say it **where the keys are entered**, not only in a document nobody opens —
someone typing an API key into a form is entitled to know it is readable by their colleagues.

Do not let the presence of roles, precedence rules and an approval queue imply otherwise. They
answer "who is allowed to change what", which is a real and useful question. They do not answer
"who can read what".

## Phase H1 — identity and the two URLs — **done 2026-08-22**

The prerequisite. Nothing else is meaningful while every request resolves to the same principal.

- `ProxyHeaderIdentity`: reads a configurable header (default `X-Forwarded-User`), and **only**
  from a configured upstream address. A header is trivially forgeable by anyone who can reach the
  port directly, so the trust boundary is the address, not the header.
- The display name comes from a second header if present; the **id must be the immutable one**
  the directory issues, never the username — `identity.ts` already explains why.
- Two URLs, one server: `/` for everyone, `/admin` for administrators.

  **Reaching `/admin` is assumed to be restricted upstream** — decided by the user on
  2026-08-22. The proxy rule, the firewall or a separate listener decides who gets there;
  Light Code does not re-derive it. That is a coherent deployment, and it is the same shape as
  the identity decision above: the trust boundary is the network, not something we can check.

  It is worth being precise about the consequence, once: **anyone who can reach `/admin`
  directly is an administrator.** If the port is ever exposed without the proxy in front, the
  admin interface is exposed with it. `--bind` already defaults to loopback for this reason and
  the startup banner should say which of the two is live.

  The admin id list is still real and still used — it decides whose tool creations need queuing
  and whose do not — but it is not what guards the URL.
- `--admin` becomes a **boolean** meaning "open the admin URL". Administrator ids move into
  config. `--admin <id>` must be an **error** naming `--admin-id`, not silently reinterpreted:
  a flag that quietly changes meaning is the failure this CLI already learned once.
- Bootstrap: `--admin-id <id>` (repeatable) seeds the list before an admin exists to manage it.

## Phase H2 — session variables — **done 2026-08-22**

- Two scopes: **admin, for everyone**, and **user, for one person**.
- Injected into the environment of what a session runs — `execute_command`, the Python worker,
  MCP servers.
- **Admin wins.** A variable set for everyone overrides a user's own of the same name, and the UI
  says which one is in force rather than showing a value that is being ignored.
- Core seam: an optional `sessionEnv` on the execution context. VS Code supplies none.
- These are not secrets. Say so next to the field.

## Phase H3 — per-user providers — **done 2026-08-22**

- A user may add their own provider profiles and API keys.
- Today `saveProfile` is admin-only in `--server` mode (`roles.ts`). That flips: profiles become
  per-user, and what stays admin-only is the **shared** set and the defaults.
- Precedence: a user's own profile is theirs; the admin's default applies when they have none.

## Phase H4 — the programming provider — **core done 2026-08-22**

- A profile nominated for generating code. User picks; falls back to the admin's default.
- Used as a **sub-call** when `create_python_tool` / `update_python_tool` runs: the primary model
  states the intent, the programming provider writes the source, and the result goes through the
  ordinary approval prompt showing the full text (§13 — approval shows what will actually run).
- Core seam: an optional code-generation hook. Absent, the primary model writes the source as it
  does now, so the extension is untouched.
- **Deviation from "node host only", recorded deliberately.** The generator is built in core's
  bridge from a `programmingProfileId` config key, not in `apps/host`. Building a provider means
  auth strategies, TLS material and the wire adapter — the most security-sensitive construction
  in the product — and duplicating that outside core to keep the feature host-only would be a far
  worse trade than one config key that is absent by default. The extension gains an opt-in key it
  never sets. The *admin default* half stays host-only.
- **Not yet built:** the picker in the UI, and the admin default falling through to a user who has
  not chosen. Configured today by setting `programmingProfileId` in config.
- Cost is metered and attributed, like the expert's. **Not built yet either.**

## Phase H5 — the approval queue

- A tool or skill written by a non-admin is staged, not registered: no hash entry, not loadable,
  not callable.
- The turn is told it was submitted and carries on. Nothing waits on a human being at a screen —
  a blocking approval would hang a scheduled run forever.
- Admins review in the admin UI with the **full source**, and approve or reject with a reason the
  author sees.
- Approval records the hash of exactly what was shown, reusing `python/registry.ts` — the
  registry is already the security boundary, and this adds who approved it and when.
- An admin's own creation keeps the ordinary in-chat prompt they already get.

---

## Sequencing

H1 first and alone: it is the prerequisite, and it is also the piece most likely to need changing
once it meets a real proxy. H2 and H3 are independent of each other. H4 needs H3. H5 needs H1.
